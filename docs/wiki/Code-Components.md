# Code Components

A code component (`kind: "code"`) is a **pure render function** executed in a capability-less QuickJS-in-WASM sandbox:

```js
render({ props, frame }) => FragmentNode[]   // text/rect/image nodes only
```

Code adds **logic** to the declarative universe, never capabilities. The output is nodes, never SVG — it flows through the exact same gates as declarative fragments (node schema validation, scaling into the instance box, animation compositing, the output sanitizer). Everything on [Declarative Components](./Declarative-Components.md) about node shapes, animations, fonts, and scaling applies to what your `render()` returns.

`render` may be a `function render() {}` declaration or a top-level `const render = ...`. It must return **synchronously** — a returned Promise/thenable is an error. `props` are your declared props with instance values merged over the defaults (`series` props arrive as raw JSON arrays); `frame` is your declared `{w, h}`.

## A first complete component

The definition is the same document as a declarative component, plus `kind: "code"` and the `code` source. `nodes` becomes an *optional* static palette preview (`[]` or absent is fine):

```json
{
  "id": "you/percent-bar",
  "title": "Percent bar",
  "category": "stats",
  "kind": "code",
  "frame": { "w": 480, "h": 40 },
  "props": {
    "label":   { "type": "string", "description": "Caption", "default": "Progress" },
    "percent": { "type": "number", "description": "0-100", "default": 62 }
  },
  "code": "function render({ props, frame }) {\n  var pct = Math.max(0, Math.min(100, props.percent));\n  return [\n    { id: \"label\", type: \"text\", x: 0, y: 0, w: frame.w, h: 16,\n      text: props.label, style: { fontSize: 12, color: \"#7d8590\" } },\n    { id: \"track\", type: \"rect\", x: 0, y: 24, w: frame.w, h: 8,\n      style: { fill: \"#21262d\", radius: 4 } },\n    { id: \"fill\", type: \"rect\", x: 0, y: 24, w: frame.w * pct / 100, h: 8,\n      style: { fill: \"#58a6ff\", radius: 4 },\n      animation: { preset: \"growX\", durationMs: 900 } }\n  ];\n}",
  "nodes": []
}
```

The source, readable:

```js
function render({ props, frame }) {
  var pct = Math.max(0, Math.min(100, props.percent));
  return [
    { id: "label", type: "text", x: 0, y: 0, w: frame.w, h: 16,
      text: props.label, style: { fontSize: 12, color: "#7d8590" } },
    { id: "track", type: "rect", x: 0, y: 24, w: frame.w, h: 8,
      style: { fill: "#21262d", radius: 4 } },
    { id: "fill", type: "rect", x: 0, y: 24, w: frame.w * pct / 100, h: 8,
      style: { fill: "#58a6ff", radius: 4 },
      animation: { preset: "growX", durationMs: 900 } }
  ];
}
```

Notice what a declarative component could only do with a `computed` mapping — `w: frame.w * pct / 100` — is just arithmetic here.

## The full walkthrough: the contribution heatmap starter

This is the **"Code: Contribution heatmap"** starter the editor's **New component** dialog seeds (frame `686 × 110`, suggested name `contribution-heatmap`), verbatim from `apps/web/src/lib/componentTemplates.ts`. It draws 371 cells — exactly what declarative fragments cannot express.

**1. The series prop.** The starter declares two props:

- `label` — `string`, default `"1,204 contributions in the last year"` (caption above the grid);
- `calendar` — **`series`**, default: a deterministic 371-entry sample array (53 weeks × 7 days), description "Daily counts, oldest first — bind github stats.calendar, or numbers/{count} objects".

The default is generated by a hash, not `Math.random` — deliberately, because the seeded draft must publish verbatim and *publish executes the code twice and byte-compares* (sample data lives outside the sandbox, but the invariant is kept everywhere on principle).

**2. Reading the series defensively.** A series element may be a bare number or a `{date, count}` object, and consumers can bind anything — so normalize:

```js
function render({ props, frame }) {
  // GitHub-style contribution heatmap: 53 week-columns, days run down each
  // column. Accepts a series of {date, count} objects (or bare numbers).
  var days = Array.isArray(props.calendar) ? props.calendar : [];
  var count = Math.min(days.length, 371); // 53 weeks x 7 days
  var cell = 10;
  var gap = 3;
  var top = 22;
  var ramp = ["#161b22", "#0e4429", "#006d32", "#26a641", "#39d353"];
  function at(i) {
    var d = days[i];
    var n = typeof d === "number" ? d : d && typeof d.count === "number" ? d.count : 0;
    return isFinite(n) && n > 0 ? n : 0;
  }
```

`at(i)` collapses every element shape to a non-negative finite number. `count` is capped at 371 so an oversized array can't blow the node budget. The `ramp` is the GitHub-dark green ramp: index 0 is the "no activity" cell color, 1–4 are increasing intensity.

**3. Scaling to the data.** One pass finds the max so intensity is relative:

```js
  var max = 0;
  for (var i = 0; i < count; i++) {
    if (at(i) > max) max = at(i);
  }
```

**4. The label node** — frame-relative, like every output node:

```js
  var nodes = [
    {
      id: "label",
      type: "text",
      x: 0,
      y: 0,
      w: frame.w,
      h: 14,
      text: props.label,
      style: { fontSize: 11, color: "#7d8590" }
    }
  ];
```

**5. Grid math + level ramp.** Index `j` runs oldest-first; columns are weeks (`Math.floor(j / 7)`), days run **down** each column (`j % 7`) — the GitHub calendar layout. The level function maps 0 to level 0 and everything else onto 1–4 proportionally to `max`:

```js
  for (var j = 0; j < count; j++) {
    var v = at(j);
    var level = v === 0 ? 0 : Math.min(4, 1 + Math.floor((3 * v) / max));
    nodes.push({
      id: "d" + j,
      type: "rect",
      x: Math.floor(j / 7) * (cell + gap),
      y: top + (j % 7) * (cell + gap),
      w: cell,
      h: cell,
      style: { fill: ramp[level], radius: 2 }
    });
  }
  return nodes;
}
```

Every cell id is unique (`d0`…`d370`); output totals ≤ 372 nodes — under the 512 cap. The frame fits the drawing exactly: `53 × (10 + 3) − 3 = 686` wide, `22 + 7 × (10 + 3) − 3 = 110` tall. (A smaller sibling of this pattern ships as the reference fixture [`examples/demo-code-component.json`](https://github.com/PengLx/makeitbeauty/blob/main/examples/demo-code-component.json).)

## The sandbox rules

Hard limits (`DEFAULT_LIMITS` in `packages/sandbox/src/limits.ts`, verbatim):

| Limit | Default | Enforced |
|---|---|---|
| `cpuMs` | 50 | interrupt handler vs. monotonic host deadline |
| `memoryBytes` | 32 MiB (`32 * 1024 * 1024`) | QuickJS runtime allocator limit |
| `maxNodes` | 512 | host-side after parse |
| `maxSourceBytes` | 64 KiB (`64 * 1024`) | host-side (UTF-8), before any context is created |
| `maxOutputBytes` | 512 KiB (`512 * 1024`) | in-sandbox UTF-16 pre-check (never pull oversized strings), then authoritative host-side UTF-8 check |

**Removed capabilities** (exact lists from the sandbox README):

- **Throwing stubs** whose message explains that determinism is enforced: `Date` (also excluded at the QuickJS intrinsic level — the real constructor never exists), `Date.now`, `Date.parse`, `Date.UTC`, `Math.random`.
- **Guaranteed absent** — scheduling: `setTimeout`, `setInterval`, `clearTimeout`, `clearInterval`, `setImmediate`, `clearImmediate`, `queueMicrotask`, `requestAnimationFrame`, `cancelAnimationFrame`; host reach: `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `Worker`, `SharedWorker`, `importScripts`, `require`, `module`, `exports`, `process`, `global`, `window`, `self`, `document`, `navigator`, `localStorage`, `sessionStorage`, `indexedDB`, `caches`; entropy/clocks: `crypto`, `performance`; QuickJS std-lib/CLI helpers: `std`, `os`, `scriptArgs`, `print`, `gc`, `load`, `read`, `readbuffer`, `quit`.
- `console` is replaced with a bounded capture (see Debugging). `eval`/`Function` remain available — they evaluate inside the same capability-less context and add nothing. The `__mib_` global prefix is reserved by the engine.

**Determinism** is enforced by the runtime, not by trust: no clocks, no entropy, no async, and a fresh context per execution (no state survives between renders or users). On top of that, **publish executes your `render()` twice against the declared prop defaults and byte-compares the two outputs** — any difference is a rejection. The code is evaluated as a classic script, so `import`/`export` are syntax errors.

Policy for violations: **publish-time rejection; render-time placeholder + warning — never a failed render.**

## Series props

- **Declaring:** `"type": "series"` with a required array `default` (≤ 1024 items; elements are unconstrained JSON — numbers, or objects like `{date, count}`).
- **Binding (consumer side):** a series prop value must be an array — either a literal one, or a **sole `"{{path}}"` template** (e.g. `"{{github.stats.calendar}}"`) which resolves to the **raw array** at that path, passed through untouched, never stringified. Anything else — a missing path, mixed text around a template, a scalar — warns and falls back to your declared default.
- **Defaults do double duty:** they are the input publish validation executes against (twice, byte-compared) *and* what palette hover previews render — so make them representative, and make them deterministic.

Series props are the one place arrays flow into components, and code components are the only consumers — a `{{props.x}}` template of a series in a declarative fragment renders an em-dash.

## Output rules

Your returned array must satisfy all of:

1. **`text`/`rect`/`image` nodes only** — an `instance` node in output is rejected (code can never smuggle a nested expansion), and so is any other `type`.
2. **Valid node shapes** — the array is ajv-validated against the same fragment-node schema as declarative components (see the node tables on [Declarative Components](./Declarative-Components.md)).
3. **Unique `id`s** within the output (the `{instanceId}__` prefix keeps ids unique *across* instances only when they are unique within one output).
4. **≤ 512 nodes**, ≤ 512 KiB serialized.
5. **Frame coordinates** — position everything relative to `(0,0)`–`(frame.w, frame.h)`; expansion scales and offsets into the instance box exactly like a declarative fragment.
6. **Built-in fonts only** in `style.fontFamily` — literal `"Inter"`, `"JetBrains Mono"`, or `"Lora"`; a template there fails the check.
7. **Animations are allowed on output nodes** — any of the 8 presets. (As with declarative fragments: if the design animates the instance itself, per-node animations are stripped with a warning and the whole component animates as one layer.)

Output strings resolve against a **props-only scope**: if your code emits `"{{github.user.followers}}"` into a text node, it renders as an em-dash with a warning — code output gets no more data than the code itself.

## `SandboxError` codes

Every sandbox failure is one typed error. At publish it is a rejection with the message below; at render it degrades to the dashed placeholder plus a warning.

| Code | What it means to you | Most common fix |
|---|---|---|
| `compile_error` | Syntax error, or source over `maxSourceBytes` (64 KiB UTF-8) | Fix the syntax the message points at; trim the source (it's counted in UTF-8 **bytes**, not characters). Remember `import`/`export` are syntax errors here. |
| `runtime_error` | Your code threw (message includes the sanitized sandbox stack) | Read the stack; the usual cause is indexing into a series element shape you didn't normalize — guard like the heatmap's `at(i)`. |
| `timeout` | CPU budget (50 ms) exceeded | Kill accidental O(n²) work over the series; cap iteration like `Math.min(days.length, 371)`. |
| `memory` | 32 MiB allocator limit exceeded | Don't build huge intermediate arrays/strings; emit nodes directly. |
| `not_a_function` | No `render`, or `render` is not callable | Define exactly `function render({ props, frame }) {…}` or `const render = …` at the top level. |
| `async_result` | `render` returned a Promise/thenable | Make it synchronous — drop `async`/`await`; there is nothing to await in the sandbox anyway. |
| `output_too_large` | Serialized output over 512 KiB, **or** more than 512 nodes (the message distinguishes the two) | Reduce cell counts; merge decorative rects; cap loops on the series length. |
| `output_invalid` | Output not JSON-representable, not valid JSON, or not an array | Return a plain **array** of plain objects — no functions, no cyclic references, no top-level object wrapper. |

Note: props cross into the sandbox as JSON — non-JSON values silently drop, exactly like `JSON.stringify`.

## Debugging with `console.log`

`console.log/info/warn/error/debug` inside the sandbox are **captured** (bounded: max 32 entries of ≤ 512 chars, plus a truncation marker) and surface as render warnings prefixed with your instance id — in the Studio they appear under the preview while you build, and publish reports the sample render's output the same way. There is no other I/O; this is your printf.

## Gotchas

- **Prose must not contain literal `{{…}}`.** The props-only publish check walks *every* string in the definition — `title`, `description`, prop descriptions, preview nodes — not just templates you meant. A description like `"renders {{github.stats}}"` is a rejection; only `{{props.*}}` references pass. The one exemption is the `code` source itself (JavaScript legitimately contains `{{…}}`-looking text and never goes through the template engine).
- **No async, period.** Not `async function render`, no `.then`, no timers (they don't exist). The sandbox is synchronous by contract.
- **The 64 KB source limit counts UTF-8 bytes.** Non-ASCII comments (e.g. Chinese) cost up to 3–4 bytes per character. The output limit (512 KiB) is also an authoritative UTF-8 byte count host-side.
- **Fresh context every execution.** Globals you set do not survive to the next render — don't try to cache across calls; there is nothing to cache into.
- **`props` are data, not live objects.** They are `JSON.stringify`'d host-side and rebuilt inside the sandbox; functions and class instances don't cross.
